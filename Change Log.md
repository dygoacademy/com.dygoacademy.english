## 2026-09-20

### Fixed: Landing page vertical-centering dead space (Phase 8, priority #1)
* **Files**: [`src/app/search/page.tsx`](com.dygoacademy.frontend/src/app/search/page.tsx)
* **What**: `<main>` no longer vertically centers its content in a full-height (`min-h-dvh`) flex box. `justify-center` was dropped in favor of top-anchored responsive padding (`pt-12 sm:pt-20 md:pt-28`).
* **Why**: Flagged in a 2026-09-20 design critique of `dygoacademy.com` on iPhone/iPad. Centering short content (headline + search card) inside a full-height flex container left roughly 340px of dead space above the headline on a 768px-tall viewport, and risked pushing the headline/input below the fold on first load on a real iPhone (Safari's collapsed address bar still eats another 50–80px). The page's entire job is getting a visitor to type a word, so this was the highest-priority fix.
* **Not a regression of the 2026-09-05 `min-h-dvh` fix**: that earlier fix solved *true* vertical centering on mobile (`min-h-screen`'s fixed `100vh` overestimates visible height when the browser chrome is still expanded). It never addressed that centering itself creates dead space when content is much shorter than the viewport — a separate problem, fixed here.
* **Verified**: isolated `next dev` instance (port 3050, kept separate from the pm2-managed production `dygo-frontend`/`dygo-backend` processes) checked at 375×812 (iPhone), 768×1024 (iPad portrait), and 1024×768 (iPad landscape) — headline and search card now render immediately below the header at all three sizes instead of a third of the way down. No console errors.

### Fixed: iPad-specific hero scaling instead of a stretched phone layout (Phase 8, priority #2)
* **Files**: [`src/app/search/page.tsx`](com.dygoacademy.frontend/src/app/search/page.tsx)
* **What**: Hero headline/subcopy now scale at `sm`/`md` breakpoints — h1 `text-2xl` → `sm:text-3xl md:text-4xl`, subcopy `text-sm max-w-sm` → `sm:text-base sm:max-w-md`, gaps widened (`gap-6 sm:gap-8`). `GuestWordTrial`'s card itself is deliberately left unchanged, still reading from the shared `CONTENT_WIDTH` constant (672px) that every page/popup in the app already uses.
* **Why**: Same 2026-09-20 design critique — at both 768px (portrait) and 1024px (landscape) the page was rendering the identical phone-sized hero text, just with more margin around it, reading as an unfinished/stretched phone layout rather than a tablet-considered one.
* **Why not widen the card, or add a second column**: two of the three options raised in the critique (enlarge the card; add supporting content alongside it) were deliberately not taken. Widening the card would reopen a settled, hard-won decision — `constants/layout.ts`'s `CONTENT_WIDTH` exists specifically because this app used to have three different per-page widths drifting independently, consolidated to one shared 672px after repeated live feedback. Adding a second column of supporting content (e.g. a quizzes/classroom-groups callout) would require new marketing copy/assets that don't exist yet — out of scope for a UI fix. Scaling the existing hero content was the option that used the extra tablet width without reopening either of those.
* **Verified**: same isolated dev instance. At 768×1024: h1 renders at 36px (`md:text-4xl`, since 768px meets the `md` breakpoint), subcopy at 16px/448px max-width, card unchanged at 672px wide. At 1024×768: same scaled sizes, page fits the viewport with no scroll (`bodyScrollHeight` === `innerHeight`). At 375×812 (phone): h1/subcopy confirmed back at their original 24px/14px — the `sm`/`md` scaling doesn't affect phone width. No console errors. `tsc --noEmit` clean.
* **Phase 8 is now closed** — all 3 priority recommendations from the 2026-09-20 design critique shipped and verified. The 3 lower-priority findings (apex-domain redirect, tap affordance on the flashcard, PWA manifest/icons) remain open and unscheduled.

### Incident: production frontend outage caused by this session's own verification testing, found and fixed
* **What happened**: repeated `next dev` runs (on scratch ports, for isolated feature verification) inside `com.dygoacademy.frontend` — the same directory the pm2-managed production `dygo-frontend` process runs `next start` from — silently overwrote the production build in `.next` with dev-mode artifacts. * **Fix**: `rm -rf .next/cache` + `npm run build:prod:domain`, then verified the correct production hostnames (`api.dygoacademy.com`/`supabase.dygoacademy.com`) were actually present in the compiled output — not assumed — before restarting via `pm2`. A separate stray process holding port 3000 (`EADDRINUSE`) also needed clearing before the restart could bind. Production confirmed back up and working via a real signed-in session afterward.
* **Verification method fixed going forward**: `next dev` will not be run inside this (or any pm2-managed) project directory again for any reason. Full incident writeup, including the specific commands and reasoning, lives in `phase 9 implementation plan.md`'s new "Incident" section at the top of the file.
* **Also found, not fixed**: the bare `dygoacademy.com` domain (no `www`) intermittently returned a Cloudflare "Origin DNS error" during this session — a more serious version of Phase 8's already-logged "bare domain 404s" finding (a full tunnel-routing gap, not just a missing redirect). Noted for whenever Phase 8's remaining lower-priority findings are picked up.
